# Agents say "done" when they aren't

*Draft hot take for Front Desk Bench. Numbers are placeholders until the full run. Every claim below is a hypothesis under test, not a result.*

Agents are getting good at writing the message. A reply to a client reads well, the tone is right, and the sentence "your appointment is moved" is perfectly phrased. The failure is one level up: the agent says the job is finished when the state of the business says otherwise. The calendar still has the old slot, the reminder still points at the old day, or a text goes out during a client's quiet hours because the agent used the salon's clock instead of the client's.

That gap is what Front Desk Bench measures. It drops a model into a simulated salon day. New texts arrive between clock steps, a reminder fires on its own, a message fails to deliver, and at the end the agent must file a report to the owner. Grading uses only the final sandbox state and the action log. Three checks run on every trial: did the state end up right (Task), did the agent avoid forbidden actions such as quiet-hours texts or texts to opted-out clients (Trusted), and does the end-of-day report match what the state shows (Report fidelity). The third one is the point. A report that says "moved two appointments, all reminders updated" is a claim, and a state check can test it.

**Why state beats reading the transcript.** The obvious shortcut is to hand a transcript to a second model and ask whether the agent did the job. That judge reads what the agent said it did. The failure we care about is exactly where the agent's account and the state disagree, and a judge that only sees the account has no way to notice the disagreement. **What we expect, and what would change our mind.** We predict that frontier models will write fluent, plausible reports that over-claim on at least some trials, most likely on stale follow-ups and on failed deliveries. <!-- TODO(results): report-fidelity pass rate per model and the most-failed checks from REPORT.md. --> If the report-fidelity failures turn out to be grader artifacts (wrong rules, ambiguous prompts), the hot take collapses and we say so.

**The honest version of the claim.** This is two scenarios so far, one fictional salon, and a few trials per model. It is a small, reproducible method, not a leaderboard and not evidence about all agents. The lesson we can defend is narrower: if you grade an agent by its own account of its work, you will miss a class of errors that a check against the world would catch. <!-- TODO(results): replace with the supported finding. -->

**What could close the gap.** Give the agent tools whose results are the ground truth and make the report a function of those results, not free text. Grade the report against the same state the owner will see. Keep an LLM judge for the judgment calls that have no state to check, such as tone and whether a clarifying question was needed, and validate it against deterministic labels before trusting it.

**Context.** The false-success problem is the motivation cited in our plan: https://natesnewsletter.substack.com/p/ai-agent-false-success. <!-- TODO(author): re-read this source and confirm it says what we cite it for before submission. --> Single-customer tool-use benchmarks such as tau-bench are described in https://www.layer3labs.io/guides/tau-bench-explained as grading end state, but they do not stress a shared, time-advancing world with several customers at once. The micro1 PersonalAgentBench frames the same two questions, whether a task was completed and whether it was done in a trusted way, using single-trial human grading (https://www.micro1.ai/personal-agent-bench). This project tries a deterministic, repeated, multi-client version of that split.

**Bottom line for a builder.** If your agent reports success, check the world, not the report. A transcript tells you what the agent believed. The sandbox tells you what happened.
